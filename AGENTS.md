# AGENTS.md — CR Integration Portal

## 1. Основные правила

Codex работает с проектом на русском языке, если пользователь не попросил иначе.

Цели:
- экономно расходовать контекст и вычислительные ресурсы;
- не сканировать весь репозиторий без необходимости;
- делать минимальные безопасные изменения;
- учитывать фактическое текущее состояние проекта;
- поддерживать `PROJECT_STATE.md` как единую компактную память о текущем состоянии системы.

Приоритет:
```text
текущая задача пользователя
> текущий код / рабочее дерево / migrations / runtime
> PROJECT_STATE.md
> последнее подтверждённое ТЗ
> остальная документация
> старые обсуждения
```

Текущее рабочее дерево включает закоммиченные и незакоммиченные изменения.

## 2. Режим стоимости задачи

Перед существенной работой внутренне выбрать минимально достаточный режим.

### ECONOM
Для поиска файлов/символов, маленьких исправлений, коротких логов, простого SQL, точечных тестов и небольших UI/backend/frontend изменений.

```text
точный поиск
→ 1–3 релевантных файла
→ минимальное изменение
→ точечная проверка
→ STOP
```

Не делать полный scan, архитектурный анализ, полный test suite или Docker rebuild без причины.

### NORMAL
Режим по умолчанию для обычной разработки: bugfix, API, CRUD, Bitrix sync, небольшие migrations, dashboard, jobs, бизнес-логика.

```text
точечный поиск
→ понять затронутый путь
→ короткий план при необходимости
→ локальная реализация
→ релевантные проверки
→ STOP
```

### COMPLEX
Только для архитектуры, race conditions, целостности данных, сложных migrations, серьёзных OAuth/token-flow изменений, крупных cross-module изменений и сложных production-only ошибок.

Даже COMPLEX не означает «просканировать всё».

Всегда начинать с самого дешёвого безопасного режима:
```text
ECONOM → NORMAL → COMPLEX
```

После нахождения причины снова сужать работу:
```text
COMPLEX investigation → NORMAL implementation → ECONOM verification
```

## 3. Экономия контекста

Каждое чтение файла, поиск, команда, тест, build и запрос логов должны отвечать на конкретный вопрос.

Перед дорогим действием определить:
```text
Какую конкретную неопределённость устранит это действие?
```

Если ответа нет — действие не выполнять.

Предпочитать точный поиск символа вместо чтения множества директорий, targeted test вместо полного suite, короткий tail логов вместо всех логов.

Не перечитывать неизменившиеся файлы без причины. Не исследовать `vendor`, cache, generated/build directories и зависимости без необходимости. Не исследовать frontend для подтверждённой backend-only проблемы и наоборот.

## 4. PROJECT_STATE.md — память проекта

`PROJECT_STATE.md` — каноническое компактное описание ТЕКУЩЕГО состояния CR Integration Portal.

В начале каждой существенной новой задачи:
1. Прочитать `PROJECT_STATE.md`.
2. По нему определить нужный subsystem.
3. Проверить только исходники, относящиеся к задаче.
4. Не восстанавливать общий контекст из старых чатов.
5. Не сканировать весь репозиторий без реальной необходимости.

Если `PROJECT_STATE.md` отсутствует или помечен как не сверенный:
1. Выполнить `git status`.
2. Проверить релевантный `git diff`, включая незакоммиченные изменения.
3. Точечно проверить фактические models, migrations, APIs, integrations, jobs, frontend и бизнес-логику.
4. Старое ТЗ использовать только для понимания бизнес-смысла.
5. Описывать то, что существует СЕЙЧАС.
6. Неподтверждённое записывать в «Известные пробелы / неопределённости».

После существенной задачи обязательно обновлять `PROJECT_STATE.md`, если изменились:
- архитектура;
- ответственность модулей;
- важные API-контракты;
- схема БД или поведение данных;
- Bitrix OAuth/auth/sync;
- background jobs;
- KPI/bonus/business rules;
- active-deal logic;
- «Ответственный за внедрение»;
- исторические данные;
- deployment/runtime;
- конфигурация;
- основные UI-процессы;
- известные проблемы;
- статус крупных функций.

### Обязательная финальная сверка PROJECT_STATE.md

Перед завершением каждой существенной задачи Codex обязан проверить:

```text
Изменилось ли фактическое текущее состояние проекта
относительно PROJECT_STATE.md?
```

Если да:
1. Не ждать отдельной команды пользователя.
2. В рамках этой же задачи проверить только затронутые разделы `PROJECT_STATE.md`.
3. Обновить их по фактически реализованному состоянию.
4. Удалить сведения, которые стали устаревшими.
5. Добавить новые существенные бизнес-правила, API-контракты, модели, migrations, процессы или ограничения.
6. Если известная проблема исправлена — удалить её из списка актуальных проблем.
7. Обновить дату сверки, если была выполнена содержательная сверка изменённой области.

Если нет:
- `PROJECT_STATE.md` не изменять;
- не делать косметические изменения только ради отметки.

Эта проверка является частью Definition of Done.

Codex не должен завершать существенную задачу с заведомо устаревшим `PROJECT_STATE.md`.

Не нужно заново анализировать весь проект: проверяется только область, затронутая текущей задачей.

Пример:

```text
изменена логика расчёта премии
→ проверить раздел KPI/премий в PROJECT_STATE.md
→ актуализировать его и связанные важные сведения
→ не перечитывать весь backend/frontend
```

Не обновлять из-за опечаток, форматирования, комментариев и рефакторинга без изменения поведения.

При обновлении заменять устаревшую информацию, удалять исправленные проблемы и никогда не записывать secrets/tokens/passwords/API keys.

Новый Codex-чат должен понимать проект в основном из:
```text
AGENTS.md
+
PROJECT_STATE.md
+
только релевантные текущей задаче исходники
```

## 5. Архитектура

CR Integration Portal — внутреннее веб-приложение вокруг данных Bitrix24.

```text
Browser → Frontend → Backend API → PostgreSQL / Redis / Bitrix24 REST/OAuth
```

Данные Bitrix24 синхронизируются в PostgreSQL. Dashboard, KPI, bonus, reports и аналитика работают по локальным данным.

Известный стек:
- Backend: Python, FastAPI, async SQLAlchemy, Alembic, PostgreSQL, Redis, httpx.
- Frontend: React + TypeScript.
- Docker Compose.
- Production: Nginx.
- SSL: Let's Encrypt / Certbot.

Backend ожидается в `backend/src/cr_portal/`.
Bitrix integration — в `backend/src/cr_portal/integrations/bitrix/`.
Фактический код имеет приоритет, если структура изменилась.

## 6. Bitrix24

Не придумывать category IDs, stage IDs, custom/user field IDs, portal-specific IDs и бизнес-правила.

Никогда не выводить и не документировать access token, refresh token, client secret, passwords и другие секреты.

Не заменять OAuth на webhook без явного решения пользователя.

Для `401 Unauthorized`, `wrong_client`, `expired_token` проверять:
```text
installation
→ client credentials/config
→ token validity
→ refresh
→ сохранение новых tokens
→ фактический API request
```

Не менять unrelated sync-логику, пока auth path не проверен.

## 7. Бизнес-правила

`Ответственный за внедрение` — отдельный бизнес-концепт и не должен автоматически равняться Bitrix `assignedById`.

Известное нормализованное поле:
`implementation_responsible_user_id`.

Известные рабочие воронки:
- CR Start
- Внедрение
- Сопровождение
- Тех интеграция

Активность сделки определяется фактической семантикой Bitrix stages / нормализованными статусами.

Исторические числовые snapshots нельзя hardcode. Inactive users могут быть нужны для истории. Исторический KPI должен сохранять исторический смысл результатов. Бизнес-правила должны поддерживать versioning там, где это требуется.

## 8. База данных

Перед изменением схемы проверить model, релевантные migrations, schemas/services и зависимые queries.

Persistent schema changes — через Alembic. Не переписывать старые применённые migrations. Сохранять данные и избегать destructive migrations.

SQL-диагностика должна быть точечной. Secrets маскировать.

## 9. Backend и Frontend

Backend: сохранять существующее разделение routes/schemas/services/models/integrations/jobs. Не помещать крупную бизнес-логику в routes. Сохранять async patterns.

Frontend: сначала найти конкретную page/component, её API call и types. Shared components смотреть только при необходимости. Использовать существующие API client, types, layout и styling. Не добавлять крупную UI-библиотеку ради маленькой задачи.

## 10. Docker и production

Ожидаемые сервисы: backend, frontend, postgres, redis.

PostgreSQL/Redis не должны публично экспонироваться.

Без явной необходимости не выполнять destructive действия, удаление volumes, пересоздание production DB, `docker system prune -a`.

Не менять Nginx/SSL/networking для обычного application bug, если проблема не инфраструктурная.

## 11. Проверки

Использовать:
```text
изменённая функция
→ затронутый модуль
→ сервис
→ integration
→ full regression/build
```

Остановиться на минимальном достаточном уровне.

Не запускать `docker compose up -d --build` после каждой маленькой правки.

Test commands не угадывать: при необходимости проверить `backend/pyproject.toml` и `frontend/package.json`.

## 12. Диагностика

```text
1. Зафиксировать точную ошибку.
2. Найти exact error/symbol.
3. Определить узкий execution path.
4. Найти root cause.
5. Сделать минимальный безопасный fix.
6. Проверить затронутый path.
7. STOP.
```

Если пользователь просит только исследовать/диагностировать/найти причину — код не менять. Вернуть root cause, подтверждения, затронутые файлы и предлагаемый минимальный fix.

Логи начинать с:
```bash
docker compose logs --tail=100 <service>
```

## 13. PowerShell

Пользователь часто работает из Windows PowerShell:
```text
PowerShell → docker compose exec → sh
```

Учитывать quoting. Избегать сложных вложенных кавычек, если можно дать простой вариант.

## 14. Git

Исторически использовалась ветка `develop`, но текущую ветку проверять при необходимости.

Без запроса не выполнять force push, reset, rebase, discard изменений или переключение веток.

Незакоммиченные изменения пользователя нельзя терять.

## 15. Приоритет изменения кода

```text
корректность
>
безопасность данных
>
совместимость с существующей архитектурой
>
маленький diff
>
«красивое» решение
```

## 16. Планирование

Маленькая задача — без большого плана.
Средняя/рискованная — короткий план 3–6 шагов.
Подробный план — только для крупных features, schema redesign, крупных Bitrix sync изменений, архитектуры или production deployment.

## 17. Definition of Done

Задача завершена, когда:
- запрошенное поведение реализовано;
- unrelated-код не изменён;
- релевантная проверка пройдена;
- migration добавлена при необходимости;
- secrets не раскрыты;
- выполнена финальная сверка актуальности `PROJECT_STATE.md`;
- `PROJECT_STATE.md` обновлён в рамках этой же задачи, если фактическое состояние существенно изменилось;
- перечислены изменённые файлы и проверки;
- известные ограничения указаны.

После этого — STOP.

## 18. Краткое правило

```text
ПРОЧИТАТЬ PROJECT_STATE
→ ИСКАТЬ ТОЧЕЧНО
→ ЧИТАТЬ МИНИМАЛЬНО
→ МЕНЯТЬ ЛОКАЛЬНО
→ ТЕСТИРОВАТЬ ТОЧЕЧНО
→ АКТУАЛИЗИРОВАТЬ PROJECT_STATE
→ КРАТКО ОТЧИТАТЬСЯ
→ STOP
```
