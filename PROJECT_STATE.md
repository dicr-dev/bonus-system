> 27 октября 2026, локально добавлен администраторский раздел «CR Логистика → Привязка топливных карт» (`/logistics/fuel-card-bindings`). Он принимает один `.xlsx`: в строке ТС должны быть госномер, `id` и до четырёх брендовых колонок карт — ТАИФ/Tatneft, Делкойл/Azimuth, Газпромнефть/Gazpromneft, Роснефть/Rosneft. Каждая непустая брендовая ячейка создаёт отдельную привязку; preview исключает повторы и строки без госномера или ID. Импорт ищет реальную строку заголовков среди первых 20 строк; распознавание нечувствительно к пробелам, точкам, скобкам и техническим пояснениям, поддерживая, в частности, `Номер`, `Гос. номер`, `Регистрационный номер`, `ID ТС`, `ID машины`, `Номер карты ТАИФ (Tatneft)`. Backend повторно строит preview и применяет только проверенно выбранные ключи строк. По отдельному подтверждению backend отправляет корректные строки в CargoRun `POST https://delko.cargorun.ru/api/fuelCards/apply`. Временный Bearer-токен поступает только в request применения, не хранится в БД, не возвращается API и не записывается в логи. Максимум — 5 000 строк и 10 МБ на файл; доступ к preview/apply — только admin. Новые migration и фоновые задачи не нужны. > 20 октября 2026, локально реализован ручной учёт качества обучений. Администратор: «Аналитика → Качество обучений» (`/analytics/training-quality`) и кнопка «Транскрибации и оценки» в каждой строке «Сделок». Для сделки можно создать несколько обучений: фактическая дата, модуль, номер 1–3, явно выбранный сотрудник отдела внедрения (включая неактивных для истории) и его точное обозначение в диалоге. Автор обучения фиксируется отдельно от текущего ответственного сделки; ФИО сохраняется snapshot. Один исходный DOCX на обучение, до 10 МБ: оригинальные bytes и SHA-256 хранятся в PostgreSQL, а не в эфемерном контейнере; файлы входят в backup БД. Синхронизация Bitrix эти записи не меняет. Чтение основного OOXML ограничено размером/числом элементов; DTD/entities запрещены, ссылки/вложения/макросы не исполняются. При наличии заголовка «Транскрипт» оценочный текст исключает готовое резюме, обнаруживаются участники/метки; дату администратор подтверждает вручную.
>
> Внешних запросов, API-ключей и локальной ИИ-модели нет: администратор скачивает TXT-задание с исходным диалогом и критериями, самостоятельно передаёт ChatGPT, затем вставляет JSON. Промпт отделяет недоверенные реплики от инструкций, оценивает указанного сотрудника и требует обоснования/точных цитат. Импорт проверяет идентификаторы обучения/версии, полный уникальный набор критериев, конечные баллы 0–10, наличие цитат в тексте и их соответствие указанному временному блоку. Итог 0–100 вычисляет сервер: сумма `балл × вес / 10`. Недостаток данных — null; при любом null общего балла нет, веса не перенормируются. Черновик сохраняется отдельно, только явное подтверждение администратора включает результат в рейтинг. Новые оценки/версии добавляются без изменения прежних; повторное подтверждение идемпотентно. Это рекомендательная оценка обучения, не автоматическое решение о премии.
>
> Начальные веса: потребности 15%, структура/время 15%, понятность 15%, практика 25%, вопросы/возражения 15%, следующие шаги 15%. Администратор создаёт новые неизменяемые версии критериев (редактор JSON, уникальные коды, сумма целых весов 100%). ## Назначение и архитектура

CR Integration Portal — внутреннее приложение для работы с локально синхронизированными данными Bitrix24: сделками, задачами, KPI отдела, премиями и отчётами. Основной путь данных: Bitrix24 REST/OAuth → PostgreSQL → API FastAPI → React-интерфейс. Redis используется для очереди, статусов и блокировки синхронизаций.

- Backend: Python 3.12, FastAPI, async SQLAlchemy, Alembic, PostgreSQL, Redis, httpx.
- Frontend: React 19, TypeScript, Ant Design, TanStack Query, Vite.
- Runtime: Docker Compose с сервисами `backend`, `frontend`, `worker`, `postgres`, `redis`. Backend и frontend опубликованы только на localhost (`8000` и `3000`), БД и Redis остаются во внутренней сети Compose.
- API: `/api/v1`. Сессия — cookie SessionMiddleware; в production включается `https_only`.

Ключевые каталоги: `backend/src/cr_portal/`, `backend/migrations/versions/`, `frontend/src/`.

## Авторизация и Bitrix24

Есть две точки входа.

1. Администратор входит через `POST /api/v1/auth/login` с `ADMIN_LOGIN`/`ADMIN_PASSWORD`; сессия привязывается к активному локальному пользователю-администратору.
2. Сотрудник входит через `GET /api/v1/auth/bitrix/login`: OAuth code flow, callback `/auth/bitrix/callback`, поиск/создание локального пользователя и запись его Bitrix ID в сессию. После входа пользователь без прав администратора видит только свои данные и разделы: главная, моя премия, мои сделки, инструкция, адаптация.

Установка Bitrix-приложения поддерживается маршрутами `/auth/bitrix/install` и `/auth/bitrix/app`. Таблица `bitrix_installations` хранит `member_id`, домен, endpoint, access/refresh token и срок действия. Значения секретов в документацию не записываются.

`BitrixClient` работает через REST endpoint установки либо через webhook из конфигурации. При `401`, `expired_token`, `invalid_token` или `no_auth_found` он один раз обновляет OAuth token и повторяет запрос. Обновлённые token и срок сохраняются в БД. Для всех закрытых `/api/v1/*` требуется сессия; `current_user` дополнительно требует активного синхронизированного пользователя.

## Синхронизация и фоновые процессы

`worker` (`python -m cr_portal.workers.sync`) выполняет три задачи.

- Очередь ручной синхронизации сделок в Redis. `POST /sync/deals` создаёт job, `GET /sync/jobs/{id}` отдаёт статус; job хранится семь дней. Полная синхронизация не использует отметку последнего запуска, инкрементальная использует `updatedTime` после последнего успешного запуска.
- Ночная синхронизация в `NIGHTLY_SYNC_HOUR` (по умолчанию 02:00 `Europe/Moscow`): пользователи, сделки и задачи/записи времени за последние `NIGHTLY_TASK_MONTHS` месяцев (по умолчанию 3). Redis-lock на 4 часа не допускает параллельный ночной запуск; при ошибке записываются время попытки и текст ошибки, следующая попытка возможна не раньше чем через час.
- Ежедневный расчёт премий за текущий месяц в `DAILY_CALCULATION_HOUR` (по умолчанию 03:00 `Europe/Moscow`). Он запускается после ночной синхронизации в том же worker, использует live-данные Bitrix для задач, сохраняет новую версию расчёта для сотрудников KPI-отделов и имеет отдельные Redis-lock/статусы попытки, результата и ошибки. При неуспехе повторяется не чаще раза в час.

Ночная и ручная синхронизация используют последнюю установку Bitrix24. `sync_users` получает структуру отделов и пользователей; локально сохраняется только принадлежность к KPI-отделам. `sync_deals` получает сделки настроенных воронок, семантику стадий и настраиваемые CRM-поля; `movedTime` применяется как время закрытия финальной стадии, поскольку универсальный API сделок не возвращает `closedTime`.

Задачи и записи времени кэшируются в `bitrix_tasks` и `bitrix_task_elapsed_items`. При самом расчёте премии задача также запрашивается через Bitrix API; кэш задач пока не является единственным источником расчёта.

## Данные и связи

Основные модели PostgreSQL:

- `users`: Bitrix ID, имя, e-mail, должность, строка KPI-отделов, активность и `is_admin`.
- `deals`: нормализованная сделка Bitrix (`bitrix_id`, воронка, модуль с читаемым названием, технический ID и читаемое название стадии, статус, суммы, машины, 1С), технический ответственный, отдельный `implementation_responsible_user_id`, имя ответственного продавца, получатель бонуса за продажу, исходная сделка и исходный JSON.
- `bitrix_tasks`, `bitrix_task_elapsed_items`: снимки задач и логов времени Bitrix. Для контроля задач 1С у задачи также сохраняются постановщик, дата начала, статус и актуальный признак пустого типа задачи.
- `bonus_rules`: версионируемые правила с периодом действия и JSON-снимком конфигурации.
- `bonus_calculations` и `bonus_calculation_items`: версии месячных расчётов по сотрудникам и детальные начисления. В расчёте сохраняются snapshot правил, суммы до/после делителя, источники и диагностические замечания.
- `manual_bonus_events`: ручные события, включая корректировки периода/получателя по сделке.
- `manual_bonus_adjustments`: отдельные ручные бонусы и штрафы: сотрудник, название, начальный месяц, число месяцев, сумма за месяц и комментарий.
- `monthly_plans`, `employee_monthly_deal_plans`, `kpi_events`, `calculation_issues`, `app_settings`, `bitrix_installations`. `employee_monthly_deal_plans` — личный состав плана сотрудника отдела внедрения на месяц; он не связан с денежным KPI-планом отдела.

Alembic head — `0018_admin_sync_connection` (подтверждён на production 16.10.2026). Миграции `0001`–`0003` создают базовые сущности и поле ответственного за внедрение; `0004` добавляет KPI/премии; `0005` — редактируемые настройки; `0006` отмечает первоначального администратора; `0007` — задачи и логи времени; `0008` — сумму и режим корректировки сделки, а также `manual_bonus_adjustments`; `0009` — назначения адаптации и пункты их выполнения; `0010` — редактируемый шаблон адаптации и инструкции к разделам/пунктам; `0011` — состав личного плана сделок на месяц; `0012` — читаемая стадия и имя ответственного продавца; `0013` — читаемое название модуля из перечисления Bitrix; `0014` — постановщика, дату начала, статус и признак отсутствующего типа задачи 1С; `0015` — ID и название связанной организации у сделки. `0016` расширяет название отдела; `0017` создаёт историю стадий, каталог полей и сохранённые отчёты; `0018` изолирует административные OAuth-токены синхронизации. При развёртывании схемы, ещё не дошедшей до этой версии, требуется `alembic upgrade head`.

## Воронки, сделки и ответственность

Настройки Bitrix в `app_settings` задают ID четырёх воронок: `tech_integration` (Техинтеграция), `implementation` (Внедрение), `cr_start` и `support` (Сопровождение), а также коды CRM-полей. Их значения не захардкожены в коде и должны заполняться администратором.

Статус сделки нормализуется из семантики стадии Bitrix в `in_progress`, `won`, `lost`. Активные списки основаны на `in_progress`, а не на предположениях о номерах стадий.

«Ответственный за внедрение» — отдельное бизнес-поле сделки, не равное `assignedById`. При синхронизации ID из настраиваемого поля сопоставляется с локальным пользователем и записывается в `implementation_responsible_user_id`. Он определяет видимость сотрудника, адресата большинства премий, показатели главной и KPI отдела.

## KPI отдела и отчёты

«Эффективность сотрудников» доступна только администратору и работает по локальным сделкам/переходам стадий. По умолчанию — текущий месяц. Закрытия относятся к месяцу фактического завершения, новые сделки — к созданию; успешность определяется семантикой `won`, выполнение отдельных KPI-флагов не оценивается. Состояние фиксируется на конец выбранного периода (для текущего периода — на момент построения); длительность считается за весь срок сделки, не только внутри фильтра. Переводы между менеджерами не реконструируются: все показатели принадлежат текущему ответственному за внедрение. Планы, нормативы длительности и оценочные баллы не применяются.

Раздел **KPI отдела** доступен администратору.

- План хранится по месяцу в `monthly_plans` и редактируется через `PUT /kpi/plan`.
- Факт — сумма `opportunity` сделок, переданных на подписку: выигранные сделки Внедрения, закрытые в выбранном месяце, и активные CR Start с датой коммерческого использования в выбранном месяце.
- В сводке также выводится процент выполнения плана: `факт / план × 100`; при нулевом плане его значение — `0%`.
- Факт разложен на Внедрение и CR Start. Списки закрыты по умолчанию в UI.
- Отдельно выводится сворачиваемый список планируемых передач: только активные Техинтеграция и Внедрение с расчётной датой перевода на подписку в выбранном месяце; показываются номер/название, дата, сумма и число машин.

Главная страница для счётчиков сделок, ежемесячной суммы, машин, 1С-интеграций, распределения по воронкам и ответственным учитывает только активные сделки «Техинтеграции» и «Внедрения»; блок переданных на подписку остаётся отдельным показателем. Для сотрудника все выборки ограничены его `implementation_responsible_user_id`; администратор видит отдел и блок сделок без ответственного.

Маршруты отчётов: `/reports/dashboard`, `/reports/my-deals-in-work`, `/reports/department-deals`; есть экспорт Excel `/reports/export/excel`. Сделки и задачи в расшифровках используют Bitrix-ссылки, открывающиеся в новой вкладке. Строка задачи — «номер — название», сделка показывается отдельной кликабельной колонкой.

## Премии и KPI: действующие правила

В расчёт премий попадают только **активные сотрудники** отделов «Отдел внедрения» (Bitrix department ID `20`) и «Разработка 1С» (ID `33`). Фильтрация применяется в синхронизации, расчёте, списке результатов и административных ручных корректировках.

Правила выбираются по расчётному месяцу, имеют версию и сохраняются в каждом расчёте. Базовый набор: делитель `2.5`, Техинтеграция `50%`, продажа `10%`, час Сопровождения `200 ₽`, обучение `2 000 ₽`, CR Start `10 000 ₽`; шкалы Внедрения и текущих клиентов также редактируются в настройках. Начисления с `divider_applied=true` входят в делимый KPI, затем делятся на актуальный делитель; прямые выплаты не делятся.

- **Внедрение:** выигранная сделка учитывается в месяц закрытия и два следующих месяца, но начисления прекращаются с месяца проигрыша связанного Сопровождения того же модуля. Предыдущие месяцы сохраняются. Ставка зависит от суммы первоначальных месячных платежей внедрений, закрытых в стартовом месяце, по версии правил; проигрыш Сопровождения не уменьшает первоначальную сумму для ставок остальных внедрений. Получатель — ответственный за внедрение.
- **Техинтеграция:** выигранная сделка с признаком интеграции 1С; база — настраиваемое поле суммы за интеграцию, применяется ставка Техинтеграции и затем общий делитель.
- **Продажа:** для выигранной сделки Внедрения, закрытой в расчётном месяце, получателю из специального поля начисляется процент от `opportunity`; эта выплата прямая, без делителя.
- В верхнем блоке «Общая информация» детализации расчёта отдельно выводятся продажи и итоговая раскладка: делимая сумма KPI и результат её деления, текущие сделки, CR Start, продажи, переработки и общий итог. Делитель берётся из сохранённого snapshot правил конкретного расчёта.
- **CR Start:** активная сделка с датой коммерческого использования в расчётном месяце. Если её «Направление (Модуль)» входит в настраиваемый список модулей CR Start для расчёта как внедрение (начально: «КР Старт ТМ», «КР Старт Эксплуатация»), эта дата считается переходом на подписку, а сделка входит в трёхмесячный расчёт и шкалу Внедрения как завершённая сделка этой воронки. Остальные CR Start: если хотя бы одно настроенное поле CR Start истинно — прямые `10 000 ₽` за один месяц; если ни одно не истинно — трёхмесячная логика на основе ежемесячной суммы и общей формулы Внедрения. Получатель — ответственный за внедрение.
- **Обучение:** задача с настроенным полем «Бонус за обучение» и настроенным значением «Да». Месяц выбирается по `DEADLINE` либо `CLOSED_DATE` из настроек; получатель — исполнитель задачи. Выплата делимая.
- **Переработки:** задачи заданного Bitrix-проекта, в выбранном месяце по крайнему сроку, у исполнителей заданных отделов. Часы берутся из ручного поля либо таймера в выбранном приоритете. Они отображаются как часы и не создают денежную выплату в текущей логике.
- Задача обучения или переработки с исполнителем, отсутствующим среди локально синхронизированных пользователей, пропускается: она не блокирует расчёт премий остальных сотрудников.
- **Часы текущих клиентов:** используются записи таймера, созданные в расчётном месяце; часы относятся к автору записи. В денежный KPI попадают задачи, связанные со сделкой Сопровождения и удовлетворяющие проверке связи с внедрением/периода, а также задачи CR Start с даты коммерческого использования включительно. Ставка — часы × цена часа (базово 200 ₽), затем общий делитель. Часы CR Start до этой даты, а также задачи Техинтеграции и Внедрения, видны в расшифровке справочно, без выплаты; CR Start разделён на пункты «до комм. использования» и «при комм. использовании». Для сотрудников «Разработка 1С» даже оплачиваемые часы отображаются только справочно и не увеличивают премию.

Расчёт сохраняет новые версии по сотруднику и месяцу; список показывает только последнюю. `POST /calculations/run?month=YYYY-MM` доступен администратору и может обращаться к Bitrix за задачами. При изменении сделок, задач, правил или ручных корректировок существующий snapshot не переписывается автоматически: нужен пересчёт выбранного месяца.

## Ручные начисления и корректировки

Администратор в «Расчёте премий» управляет двумя независимыми сущностями.

1. **Корректировка начисления сделки** доступна только сделкам CR Start и Внедрения. Можно выбрать сотрудника, первый месяц и 1–12 месяцев, а также режим:
   - `formula` — применяется обычная формула сделки, но заданные период и получатель;
   - `manual_amount` — заданная сумма выплачивается каждый месяц периода напрямую, без делителя. Сумма может быть отрицательной.
   На одну сделку и тип корректировки хранится одна актуальная запись; повторное сохранение её обновляет. Миграция 0008 переносит существующие CR Start-корректировки как `manual_amount` со значением `10 000 ₽`.
2. **Ручные бонусы и штрафы** не связаны со сделкой: выбираются сотрудник, название, начальный месяц, 1–12 месяцев, ненулевая сумма за месяц со знаком и комментарий. Доступны создание, редактирование и удаление. Каждая такая сумма — прямая выплата без делителя и появляется в расчёте выбранных месяцев после пересчёта.

Старый универсальный `POST /calculations/manual-events` остаётся в API, но интерфейс для ручных корректировок использует специализированные endpoints `/calculations/deal-overrides` и `/calculations/manual-adjustments`.

## Frontend и API

Основной компонент — `frontend/src/App.tsx`; доступны страницы: главная, KPI отдела, расчёт/моя премия с детализацией и группировками, сделки, инструкция, диагностика, правила, настройки и синхронизация. Административное меню скрыто от сотрудников и backend дополнительно проверяет права.

Раздел «Адаптация» использует редактируемый администратором шаблон из разделов и пунктов. У каждого уровня есть подробная инструкция; начальный шаблон содержит 23 пункта по модулям Логистика, CR Start, Эксплуатация, Топливный модуль и Загрузки. Администратор получает и заменяет шаблон через `GET`/`PUT /onboarding/template`, назначает его активному сотруднику через `POST /onboarding/assign/{employee_id}` и видит все назначения через `GET /onboarding/`; одновременно одному сотруднику доступно одно назначение. При назначении в план копируется текущий шаблон, поэтому дальнейшие изменения не меняют уже начатую адаптацию и её факт. Сотрудник получает только своё назначение (`GET /onboarding/my`) и отмечает пункт через `PATCH /onboarding/tasks/{id}`. Завершение требует непустого итогового комментария; сохраняются статус, текст и время выполнения.

В «Расчёте премий» администратор видит сотрудников, сгруппированных по отделам, может запускать расчёт, открывать расшифровку, работать с корректировками сделок, ручными бонусами/штрафами. В расшифровке часы группируются по воронкам и списки сворачиваются. Инструкция объясняет сотрудникам, какие поля Bitrix нужны для обучения, переработок, часов текущих клиентов, продажи и CR Start.

Основные группы API: `auth`, `users`, `deals`, `reports`, `kpi`, `calculations`, `settings`, `sync`, `diagnostics`, `distribution`; прежний `bonus/calculate` сохраняется как legacy endpoint. Администратор может получить live-список пользовательских полей сделок Bitrix через `GET /settings/bitrix-deal-fields`; UI «Поля Bitrix» показывает только коды `ufCrm_`, названия и типы, с поиском и копированием кода. `health`, `health/db`, `health/redis` не требуют сессии.

## Конфигурация и развёртывание

Секреты и адреса подключения задаются через `backend/.env` и environment Compose. Значения token, паролей, `SESSION_SECRET`, OAuth client secret и webhook не должны попадать в git или этот файл.

В настройках UI администратор редактирует Bitrix category IDs, поля сделок, CR Start-поля, параметры обучения/переработок и версии правил премирования. Environment-переменные служат bootstrap-значениями: при первом доступе переносятся в `app_settings`, далее источник бизнес-конфигурации — БД.

Обычный порядок обновления: собрать изменённые образы, выполнить `docker compose exec backend alembic upgrade head`, перезапустить затронутые `backend`, `frontend` и при изменении синхронизации — `worker`; затем проверить `docker compose ps`, `alembic current` и `/api/v1/health`.

Production: последняя точечная сверка 26 октября 2026 — расширен доступ к еженедельному ОВ, backend/frontend обновлены, живой ACL и HTTPS проверены, worker/БД/OAuth не менялись. Это узкий patch поверх прежней установки, не полный перенос локального дерева; локальные migrations 0019/0020 не развёртывались. Предыдущее полное обновление 16.10 использовало исходники release `0514d18` поверх checkout `fb4f0de` со схемой `0018_admin_sync_connection`. Подробности текущего backup и проверок — в верхней записи. Расчёт премий пропускает обучающие задачи с несинхронизированным исполнителем вместо отмены всего расчёта.

## Известные пробелы / неопределённости

- Точные значения Bitrix category IDs, user-field IDs, CR Start-полей, проекта переработок и отделов переработок не зафиксированы в исходниках: они зависят от `app_settings`/окружения и должны проверяться в работающей установке.
- Фактическое состояние OAuth-настроек и доступность внешнего Bitrix24 из конкретного окружения нельзя подтвердить только по рабочему дереву.
- Кэш задач существует, но расчёт премии пока использует live-запросы Bitrix для задач и elapsed items; переход на полностью локальный расчёт не реализован.
- В коде нет отдельного механизма автоматического пересчёта исторических премий после изменения правил или ручных корректировок; это действие выполняет администратор.
- В рабочем дереве нет отдельного `PROJECT_STATE.md` до этой сверки; `PROJECT_STATE_RU.md` содержит устаревший шаблон и не является источником этого описания.
